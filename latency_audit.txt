LATENCY AUDIT OF THE _stream FILES
===================================

Read-only audit. No code was changed. SDK capabilities mentioned below were
checked against the installed packages.

FILES AUDITED (filename ends in "_stream")
  - transport/livekit_session_stream.py
  - transport/agent_connector_stream.py
  - agent_core/main_loop_stream.py
  - voice_io/tts_stream.py
  - voice_io/stt_stream.py

SKIPPED (legacy / non-streaming counterparts)
  - livekit_session.py, agent_connector.py, main_loop.py, tts.py, stt.py
  - agent_core/test_stream_loop.py (ends in "_loop", not "_stream")
  - tools.py, tool_registry.py, booking_store.py and system_prompt.py were read
    only for context. They are not audited.


FINDINGS, BIGGEST RISK FIRST
============================

1. CRITICAL: Gemini stream is consumed synchronously, so TTS effectively starts
   only after the full LLM reply
-------------------------------------------------------------------------------
Where: agent_core/main_loop_stream.py:29 and :44, consumed at
       transport/livekit_session_stream.py:64-77.

Risk:
  - client.models.generate_content_stream is the blocking sync SDK call, and
    "for chunk in stream:" is a plain sync loop inside an async generator.
  - Every wait for the next token blocks the whole event loop.
  - The "yield" in an async generator does not hand control back to the event
    loop. Nothing in the generator ever truly suspends.
  - "await sentence_queue.put()" on an unbounded queue does not suspend either.
  - So speak_sentences() never gets scheduled until the whole LLM response has
    been read. Your sentence-level pipelining does nothing.
  - The "LLM time to first sentence" log is accurate, but TTS starts much later
    than that number suggests.
  - While the loop is blocked, forward_audio stops sending mic audio to
    Deepgram. Deepgram receive and TTS receive stall, LiveKit playout can
    underrun, and current_task.cancel() cannot run.

Impact: time to first audio becomes STT end-of-turn + full LLM generation + TTS
first byte, instead of first-sentence time + TTS first byte. For a five-sentence
reply that is roughly 1-4 s of extra silence. Mic audio also freezes for that
whole span, which can make Flux miss the user's next turn or barge-in.

Fix:
  - Switch to the SDK's async streaming API
    (client.aio.models.generate_content_stream). It exists in your installed
    google-genai.
  - Iterate it with "async for", so every chunk is a real suspension point.
  - If you would rather keep the sync SDK, run the sync iteration in a worker
    thread and pass chunks back through an asyncio.Queue.
  - After this, re-measure. The TOTAL log should drop noticeably.


2. HIGH: TTS is strictly sequential, one sentence per request/flush/wait cycle
-------------------------------------------------------------------------------
Where: voice_io/tts_stream.py:86-92 (speak), driven by the loop in
       transport/livekit_session_stream.py:34-57.

Risk:
  - Each sentence is sent, flushed, then awaited until SpeakV1Flushed arrives
    before the next sentence is even sent.
  - Because capture_frame applies backpressure (LiveKit's default queue is
    1000 ms), the Flushed message is only read when the playout queue has
    drained. So sentence N+1 is requested only about 1 s before N finishes
    playing.
  - Any TTS first-byte time above that buffer, or any very short sentence
    ("Sure."), produces an audible gap.

Impact: roughly 100-400 ms of dead air per sentence boundary in the bad case,
and none in the good case. It is unpredictable, so it will sound choppy.

Fix:
  - Decouple sending from receiving. As soon as a sentence is ready, send its
    text immediately, without waiting for the previous sentence's Flushed.
  - Track the outstanding Flushed count separately, and wait for it only at the
    end of the turn.
  - Deepgram processes text messages in order, so audio stays in order.


3. HIGH: No barge-in or interrupt handling, and stale audio contaminates the
   next turn
-------------------------------------------------------------------------------
Where: transport/livekit_session_stream.py:101-109, and the shared
       _current_on_chunk / _current_done slots in voice_io/tts_stream.py:66-67.

Risk:
  - Only EndOfTurn is handled. When the user starts talking over Ava, she keeps
    speaking until the user finishes.
  - When a new turn cancels the old task, three things are left behind:
      * No Clear is sent to Deepgram TTS, although the SDK has one.
      * audio_source.clear_queue() is never called, so up to about 1 s of old
        audio still plays.
      * The old sentence's Flushed can set the next turn's _current_done,
        cutting the new reply short.
  - cancel() also does not wait for the old task to finish. Cancelling
    mid-tool-call can leave conversation_history with a function_call and no
    function_response, and Gemini will typically reject that next request,
    which means silence.

Impact: about 0.5-1.5 s of old speech before the new reply is heard. In the
worst case the next turn errors or truncates, which shows up as a long silence.

Fix:
  - On a StartOfTurn (or on cancel), do all of the following:
      * Cancel the task and await it.
      * Send Deepgram TTS a Clear.
      * Call audio_source.clear_queue().
      * Reset the per-turn TTS state.
  - Give each turn its own callback and done event, keyed by turn ID, instead
    of the single shared slot.
  - Roll back or repair the history on cancel.


4. MEDIUM-HIGH: Only the final EndOfTurn is used, with no eager/speculative
   start
-------------------------------------------------------------------------------
Where: transport/livekit_session_stream.py:93-97 and :103.

Risk:
  - Flux lets you opt into early-turn events, and the installed SDK exposes
    eager_eot_threshold and eot_timeout_ms.
  - You do not use them, so the LLM only starts after the full end-of-turn
    confidence is reached.
  - Also, user_stopped_at is stamped when the message arrives, not when the
    user actually stopped speaking. Your TOTAL metric therefore omits the
    endpointing delay and understates real latency.

Impact: typically 150-400 ms of avoidable delay, plus a metric that reads
optimistic by a similar amount.

Fix:
  - Enable the eager threshold and start the LLM speculatively on the eager
    event.
  - Cancel and restart if TurnResumed arrives, or reuse the result if the final
    transcript matches.
  - Check the Flux docs for the trade-off: more LLM calls (cost) in exchange
    for lower latency.
  - Fix the metric by using the audio timestamps Flux provides.


5. MEDIUM: First sentence must fully complete before TTS starts
-------------------------------------------------------------------------------
Where: transport/livekit_session_stream.py:67-77, regex [.!?]\s

Risk:
  - A long or clause-heavy opener ("Sure, I can help with that, let me check
    the available slots for September 20th.") holds back all speech until the
    period plus the following whitespace.
  - The trailing-whitespace requirement also delays the emit by one more token.

Impact: about 200-800 ms on long first sentences.

Fix:
  - Flush the first chunk earlier: at the first comma or clause boundary once
    it holds a minimum number of words or characters.
  - Keep sentence-level splitting for the rest.
  - Prompt the model to open with a short acknowledgement.


6. MEDIUM: Tool calls cost a full extra LLM round trip, and the tool call runs
   synchronously
-------------------------------------------------------------------------------
Where: agent_core/main_loop_stream.py:55-64.

Risk:
  - Each tool call means a second complete Gemini request, with its own time
    to first token, and the user hears nothing unless the model spoke first.
  - Tools are executed as plain sync calls in the async generator. Today they
    are in-memory and effectively free, so this is fine for now.
  - Only the last function call in a response is kept
    (tool_call = part.function_call overwrites). Parallel calls are silently
    dropped, which forces another wasted round trip.

Impact: about 0.4-1 s per tool hop today. A real DB or HTTP tool would add its
own latency and block the loop.

Fix:
  - Prompt the model to say a short filler before calling a tool, and confirm
    the loop already streams it.
  - Run every tool call from a response, concurrently, before the next LLM
    call.
  - Make tools async, or offload them to a thread.


7. MEDIUM: No timeouts or reconnect on the persistent TTS socket, so a dead
   socket stalls forever
-------------------------------------------------------------------------------
Where: voice_io/tts_stream.py:69-92 and transport/agent_connector_stream.py:33-34.

Risk:
  - The connection is created once at startup, which is good for latency.
  - There is no health check, reconnect, or timeout on
    "await self._current_done.wait()". If the socket drops or times out while
    idle, or a Flushed message is lost, every later turn hangs.
  - process_transcript awaits speaker_task forever.
  - A single shared socket and single-slot state also break with more than one
    participant.

Impact: the worst case is infinite latency, and the agent goes silent until
restart.

Fix:
  - Add a timeout on the Flushed wait.
  - On send or receive failure or timeout, reconnect and retry the sentence.
  - Consider a keepalive or a pre-warm before each turn.
  - Use one TTS connection or context per session.


8. LOW-MEDIUM: Conversation history grows without bound
-------------------------------------------------------------------------------
Where: agent_core/main_loop_stream.py:24 and :56-66, plus the global in
       transport/livekit_session_stream.py:14.

Risk:
  - The full history, including function calls and responses, is resent every
    turn and on every tool hop.
  - The system prompt is tiny (343 bytes), so it is not the issue.

Impact: a slowly growing time to first token over a long call, in the tens of
ms per several turns. It is not noticeable early.

Fix:
  - Cap the history to a sliding window and trim old tool traffic.
  - Consider thinking_level set lower if answer quality holds. It is currently
    "low".


9. LOW: STT logic is duplicated, and stt_stream.py is not in the live path
-------------------------------------------------------------------------------
Where: voice_io/stt_stream.py and transport/livekit_session_stream.py:90-119.

Risk:
  - stt_stream.py is a mic-only test harness. The live pipeline has its own
    Deepgram connection code, so there is duplicate logic to keep in sync.
  - Live path: a new AsyncDeepgramClient and connection is created per
    subscribed track, and nothing closes it on unsubscribe.
  - stt_stream.py: it uses run_coroutine_threadsafe per callback with no
    backpressure.

Impact: a one-time connect at join (about 100-300 ms), not hot path. Leaked
connections and connections opened on re-subscribe are the only ongoing cost.

Fix:
  - Reuse a single client, and close the connection when the track unsubscribes.
  - Use stt_stream.py only as a test, or delete it.


"WATCH OUT IF YOU TOUCH THIS" WARNINGS
======================================

  - get_agent_reply_stream (main_loop_stream.py): it is the whole critical
    path. Any validation, logging, RAG lookup, or analytics call added before
    the first "yield" adds directly to time to first audio. Do all of that
    concurrently, or off the path.
  - process_transcript: do not add awaited work between the LLM chunk loop and
    sentence_queue.put. Anything sitting there delays TTS. A per-sentence
    content filter or translation step is the classic offender.
  - on_chunk: any await here (recording, metrics, resampling) throttles the
    Deepgram receive loop, because it is called inline from the listen task.
  - on_message (STT): keep it non-blocking. It runs in the socket's receive
    loop, and blocking it delays all later STT events and cancels.
  - New pipeline stages (guardrails, PII redaction, translation): insert them
    in a streaming, per-sentence way, not on the full reply.
  - New tools: each one that fires adds a full LLM round trip. Keep them fast,
    async, and preceded by a filler line.
  - agent_connector_stream.py startup: tts.connect() is awaited serially before
    audio setup. It is harmless today because it is off the hot path, but keep
    any new startup work there off the per-turn path.
