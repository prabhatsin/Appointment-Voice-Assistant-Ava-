01

The runtime stack: who runs whom

There are four levels. A WorkerRunner runs one or more workers. The common worker is a PipelineWorker, which runs one Pipeline. A pipeline is an ordered list of FrameProcessors. Workers talk to each other over a message bus. A simple voice bot has exactly one worker, so you can ignore the bus until you need several agents.

Single-bot case (most code)

Build a Pipeline([...]), wrap it in PipelineWorker, add it to a WorkerRunner, call run(). See examples/getting-started/06-voice-agent.py.

Multi-agent case

Several workers call each other with jobs over the bus (pipeline/job_context.py). A pipeline can exchange frames with other workers when created with bridged=. Examples are in examples/multi-worker/.

Deprecated names you will still see

PipelineTask is now PipelineWorker, and PipelineRunner is now WorkerRunner (since 1.3.0). Old tutorials use the old names.

02

A voice agent pipeline, stage by stage

This is the canonical pipeline with your stack in it: LiveKit, Deepgram STT and TTS, and Gemini. Each box is one FrameProcessor. The arrow labels name the frame types that actually cross each boundary.

Services are just processors

STTService, LLMService and TTSService subclass AIService, which subclasses FrameProcessor. Swapping Deepgram for another vendor means swapping one box. Nothing else changes.

Provider-neutral context

LLMContext stores messages in one universal format. Each LLM service has an adapter (adapters/services/gemini_adapter.py) that converts messages and tools to its provider's format at call time.

The transport is two processors

transport.input() is the first stage and transport.output() is near the end. One transport object owns the room connection. Its input and output halves sit at opposite ends of the pipeline.

03

Inside one FrameProcessor

This is the most important mechanism in the codebase. Every processor has two queues and two asyncio tasks. Urgent frames skip the line; everything else is handled strictly in order, one at a time. Interruptions work because the ordered side can be cancelled while the urgent side keeps running.

Frame kindQueue pathOn interruptionExamples
SystemFrameHandled as soon as it arrivesNever droppedStartFrame, CancelFrame, InterruptionFrame, InputAudioRawFrame, VADUserStartedSpeakingFrame, BotStartedSpeakingFrame, ErrorFrame, MetricsFrame
DataFrameIn order, one at a timeDropped (unless uninterruptible)TextFrame, LLMTextFrame, TTSSpeakFrame, OutputAudioRawFrame, LLMMessagesAppendFrame, FunctionCallResultFrame (kept)
ControlFrameIn order, one at a timeDropped (unless uninterruptible)EndFrame (kept), LLMFullResponseStartFrame/EndFrame, TTSStartedFrame/StoppedFrame, *UpdateSettingsFrame

Input audio is a SystemFrame on purpose. Microphone audio must never wait behind a slow LLM stage, or VAD would miss the user starting to speak. Output audio is a DataFrame on purpose too. It must play in order, and an interruption must be able to throw it away.

07

How to study this codebase end to end

Order matters. Each step depends on the one before it. Plan roughly one focused session per step, and run code at every stage rather than only reading.

  1. Read the frame base classes.Top of frames/frames.py: Frame, SystemFrame, DataFrame, ControlFrame, the interruptible flag. Skim the list of subclasses without reading each one.
  2. Read FrameProcessor slowly.processors/frame_processor.py: queue_frame, push_frame, the two task handlers, _start_interruption, broadcast_frame. Redraw diagram 3 from memory afterwards.
  3. Run the smallest examples.examples/getting-started/01-say-one-thing.py then 02-llm-say-one-thing.py. Add a DebugLogObserver or set loguru to TRACE and watch frames move.
  4. Read Pipeline and PipelineWorker.How Source and Sink are added, how StartFrame, EndFrame and CancelFrame travel, what the idle and heartbeat monitors do.
  5. Run the full voice agent.06-voice-agent.py with your own keys. Then swap in LiveKit, Deepgram and Gemini one service at a time.
  6. Follow one turn through the code.Input transport, then the user aggregator's VAD and turn strategies (turns/), then LLMService, then TTSService._process_text_frame, then the output transport's audio task. Use diagram 4 as the checklist.
  7. Study context and function calling.LLMContext, the aggregator pair, adapters/services/gemini_adapter.py, register_function and run_function_calls. Run 07-function-calling.py.
  8. Write your own processor.For example, one that uppercases TextFrames, or one that counts user turns. Insert it in the pipeline and test interruptions against it. This is the moment the model clicks.
  9. Read observers and metrics.observers/user_bot_latency_observer.py and turn_tracking_observer.py. Turn on enable_metrics to see TTFB per service.
  10. Only then, the multi-worker layer.workers/, bus/, pipeline/job_context.py, and examples/multi-worker/local-handoff. It builds on everything above.

Tests are a second map of the code. tests/ has focused tests per processor that show the exact frames each component expects and emits. When a class is confusing, read its test first.
